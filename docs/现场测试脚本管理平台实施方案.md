## 一、项目背景与目标

### 1.1 现状痛点

| 痛点 | 说明 |
|------|------|
| 脚本格式不统一 | 客户不同提供的电子版脚本格式各异（Excel/Word/PDF），无法统一管理 |
| 纸质填写效率低 | 测试员现场打印表格→手写→后期录入电脑，重复劳动且易出错 |
| 审核流程不规范 | 纸质签字难以追溯，代签、漏签现象难管控 |
| 数据分散难以查阅 | 客户后期索要历史测试数据时，查找整理耗时巨大 |
| 归档混乱 | 项目结束后脚本按项目/工种/设备类型的分类归档全靠人工 |

### 1.2 建设目标

**总体目标**：建设一套支持多项目、多工种、多设备类型的现场测试脚本全生命周期管理平台，实现脚本模板管理 → 多人在线填写 → 多级审核签字 → 数据归档 → PDF导出的完整闭环。

**核心能力指标**：

- 支持 **≥40个** 脚本模板统一管理
- 支持 **≥10人** 同时在线填写同一项目的不同脚本
- 支持按 **项目 → 工种 → 设备类型** 三级分类归档
- 支持 **多级审核签字**（测试员 → 项目经理 → 客户）
- 支持填写数据 **一键打包导出 PDF**，还原纸质表格样式
- 所有数据 **持久化存储**，支持按项目/客户/时间范围检索

### 3.2 核心数据模型

```typescript
// ========== 脚本模板 ==========
interface TestScriptTemplate {
  id: string;
  name: string;                          // 模板名称
  customer?: string;                      // 适用客户
  category: '电气' | '暖通' | '弱电' | '消防' | '安装检查';  // 工种
  deviceType?: string;                   // 设备类型
  description?: string;                   // 模板描述
  fields: ScriptField[];                  // 字段定义
  approvers: ApproverConfig[];           // 审核流程配置
  createdAt: string;
  updatedAt: string;
}

interface ScriptField {
  id: string;
  type: 'step' | 'radio' | 'checkbox' | 'select' | 'text' | 'textarea' | 'number' | 'date' | 'table' | 'signature' | 'image';
  label: string;
  required: boolean;
  options?: string[];                     // 单选/多选/下拉的选项
  placeholder?: string;
  tableConfig?: {                         // 当 type === 'table' 时
    columns: { key: string; label: string; type: string }[];
    defaultRows?: number;
  };
}

interface ApproverConfig {
  level: number;                          // 审核级别（1=测试员, 2=项目经理, 3=客户）
  role: string;
  name?: string;
}

// ========== 测试实例（每个项目/每种设备创建一个实例）==========
interface TestScriptInstance {
  id: string;
  templateId: string;
  projectName: string;                   // 所属项目名称
  projectId: string;                      // 关联项目ID
  category: string;                       // 工种
  deviceType: string;                      // 设备类型
  status: '草稿' | '进行中' | '待审核' | '已完成';
  submissions: TestSubmission[];          // 每日填写记录
  signoffs: TestSignoff[];                // 审核签字记录
  createdAt: string;
  updatedAt: string;
}

// ========== 每日填写记录 ==========
interface TestSubmission {
  id: string;
  instanceId: string;
  testerId: string;                       // 测试员ID
  testerName: string;
  date: string;                            // 填写日期
  data: Record<string, any>;               // 表单数据（key-value）
  status: '待提交' | '已提交' | '被驳回';
  submittedAt?: string;
}

// ========== 审核签字 ==========
interface TestSignoff {
  id: string;
  submissionId: string;
  approverId: string;
  approverName: string;
  level: number;                           // 审核级别
  status: '待审核' | '已通过' | '已拒绝';
  comment?: string;                        // 审核意见
  signature?: string;                       // 签字图片（base64）
  signedAt?: string;
}
```

## 四、功能模块详细设计

### 4.1 模块总览

| # | 模块名称 | 功能描述 | 优先级 |
|---|---------|---------|--------|
| M1 | 脚本模板库 | 模板 CRUD、预览、复制、分类管理 | P0 |
| M2 | 字段构建器 | 可视化拖拽配置表单字段 | P0 |
| M3 | 测试实例管理 | 从模板创建实例，分配到项目/设备 | P0 |
| M4 | 每日填写中心 | 动态渲染表单，支持自动保存，多人同时填写 | P0 |
| M5 | 审核签字台 | 多级审核，Canvas 手写签名，驳回重填 | P1 |
| M6 | PDF 导出中心 | 填写数据导出为还原纸质表格样式的 PDF | P1 |
| M7 | 分类归档管理 | 项目→工种→设备类型三级分类体系 | P1 |
| M8 | 数据看板 | 按项目/客户/时间范围筛选查看历史数据 | P2 |

### 4.2 M1 — 脚本模板库

**功能描述**：统一管理所有脚本模板，支持按工种/设备类型/客户筛选。

**页面布局**：
- 左侧：三级分类树（工种 → 设备类型）
- 右侧：模板列表卡片（模板名、适用客户、字段数量、创建时间）
- 右上角：「新建模板」按钮

**支持操作**：
- 新建模板（填写基本信息 → 进入字段构建器）
- 复制模板（快速创建相似模板）
- 编辑模板
- 预览模板（查看最终表单效果）
- 删除模板（需确认）

### 4.3 M2 — 字段构建器

**功能描述**：通过可视化界面配置表单字段，无需编写代码。

**支持字段类型**：

| 字段图标 | 类型 | 说明 |
|---------|------|------|
| 📝 | 步骤 | 序号 + 描述文本，只读展示 |
| ◉ | 单选 | `☑选项A　□选项B` |
| ☑ | 多选 | `☑选项A ☑选项B` |
| ▼ | 下拉 | 下拉选择 |
| T | 文本 | 单行文本输入 |
| ¶ | 多行文本 | 多行文本输入 |
| 123 | 数字 | 数字输入 |
| 📅 | 日期 | 日期选择器 |
| ⊞ | 数据表格 | 多行多列网格（如设备巡检记录表） |
| ✍ | 签字区 | Canvas 手写签名面板 |
| 📷 | 图片上传 | 现场照片 |

**字段配置面板**：
- 点击字段可编辑：标签名、是否必填、选项列表、默认值等
- 支持拖拽调整字段顺序
- 支持字段分组（折叠/展开）

### 4.4 M3 — 测试实例管理

**功能描述**：从模板创建测试实例，分配到具体项目和设备。

**创建实例**：
1. 选择模板
2. 选择关联项目（从现有项目列表选择）
3. 选择设备类型（自动带出）
4. 设置审核流程（默认三级：测试员→项目经理→客户）
5. 确认创建

**实例列表**：
- 按项目分组展示
- 显示填写进度（已填 X/Y 天）
- 显示审核状态（待审核/已通过/已完成）
- 支持按状态筛选

### 4.5 M4 — 每日填写中心

**功能描述**：测试员每日在线填写表单，支持多人同时填写不同实例。

**核心能力**：
- **多人同时填写**：同一项目的不同测试实例可以同时被不同测试员填写，互不干扰
- **自动保存**：每 30 秒自动保存草稿，防止数据丢失
- **日期导航**：选择具体填写日期，每次填一份
- **进度显示**：显示当前实例的总填写进度

**表单渲染**：
- 依据模板字段定义动态渲染表单
- 复杂数据表格支持动态增删行
- 图片上传支持拍照或相册选择

### 4.6 M5 — 审核签字台

**功能描述**：审核人查看提交记录，填写意见，进行电子签字。

**审核流程**：
```
测试员提交
    ↓
项目经理初审（✍签字）
    ↓ 通过/驳回
客户终审（✍签字）
    ↓ 通过
✅ 项目完成，数据归档
```

**签字功能**：
- 点击「签字」弹出全屏 Canvas 手写板
- 签字保存为 base64 PNG 图片
- 签字区显示：签字人姓名 + 角色 + 时间戳
- 支持拒绝并填写驳回意见，打回重填

### 4.7 M6 — PDF 导出中心

**功能描述**：按项目/工种/时间范围打包导出测试数据。

**导出能力**：
- **单份导出**：选择一个实例，导出一份完整 PDF
- **批量打包**：选择多个实例，导出 ZIP 包（含多份 PDF）
- **按项目导出**：选择某项目下所有测试数据，一次性打包

**PDF 样式要求**：
- 完整还原纸质表格样式（保留表格线、合并单元格）
- 包含所有填写数据
- 签字区显示签字人姓名 + 时间戳 + 签名图片
- 页眉显示项目名称、模板名称、日期
- 页脚显示页码

### 4.8 M7 — 分类归档管理

**功能描述**：维护三级分类体系（项目→工种→设备类型）。

**管理功能**：
- 新增/编辑/删除设备类型
- 新增/编辑/删除工种分类
- 分类支持排序
- 分类下显示关联的模板数量

### 4.9 M8 — 数据看板

**功能描述**：统一查看所有测试数据，支持多维度筛选。

**筛选维度**：
- 按项目
- 按客户
- 按工种
- 按设备类型
- 按时间范围
- 按状态（进行中/待审核/已完成）

**展示内容**：
- 各项目测试进度概览
- 待审核事项提醒
- 历史数据快速检索

### 5.2 Excel 批量导入方案

针对现有 40 个脚本文件，提供批量导入工具：

```
scripts/
└── import_templates.py     # Excel 解析 + 模板生成脚本

输入：40个Excel/Word文件（原始脚本）
处理：
  1. 解析每个Excel的Sheet结构
  2. 识别字段类型（通过表头关键词+数据特征判断）
  3. 识别签字区（通过关键词"签字""审核""签名"判断）
  4. 生成标准化 JSON 模板定义
输出：批量模板 JSON，可直接导入平台
```

**字段类型自动识别规则**：

| 识别规则 | 判断类型 |
|---------|---------|
| 表头含"电压"/"电流"/"功率" | number |
| 表头含"日期" | date |
| 内容为"☑/□"或"是/否" | radio |
| 表头含"状态"/"类型" | select |
| 行数不固定的数据网格 | table |
| 含"签字"/"审核"/"签名"关键词 | signature |
| 含"照片"/"现场"/"附件"关键词 | image |

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| Excel 表格结构过于复杂无法自动解析 | 高 | 优先处理简单脚本，复杂脚本（37个Sheet电气表）手动辅助映射 |
| 多人同时填写同一实例产生数据冲突 | 中 | 实例级别加锁机制，同一时间只允许一人填写一天的数据 |
| PDF 导出样式还原度不足 | 中 | 使用原生 HTML → PDF 方案（html2canvas + jsPDF），最大限度还原表格样式 |
| 签字数据量导致数据库膨胀 | 低 | 签字图片压缩存储，定期归档历史数据 |
| 现场网络不稳定导致提交失败 | 高 | 增加离线缓存能力（Service Worker），网络恢复后自动同步 |

## 十、结论与建议

### 推荐实施路径

```
第一步（1天）：选定一个最简单的脚本（如"消防联动测试"）
              完成从模板→填写→审核→导出的全流程 MVP 验证

第二步（1天）：根据验证结果调整技术方案和表单渲染逻辑

第三步（1天）：批量导入所有简单脚本模板（~20个）

第四步（2天）：处理复杂脚本（电气37Sheet、暖通40Sheet）
              重点解决数据表格多行多列的渲染和导出问题

第五步（1天）：多人协作+审核流程+权限体系

第六步（1天）：UAT 测试 + 上线部署
```

### 建议优先级

1. **MVP 先跑通全流程**，不要一开始就追求覆盖所有 40 个模板
2. **复杂表格（电气/暖通多Sheet）留到最后处理**，这些是差异化价值但技术难度最高
3. **签字流程和 PDF 导出是最核心差异点**，投入足够时间打磨用户体验
